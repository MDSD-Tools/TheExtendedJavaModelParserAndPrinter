# Resolving References

The extended JaMoPP provides three variants to resolve the references between different Java models introduced by, for example, imports or inheritance. This guide provides a high-level view on how the variants work. The naming of the variants is based on their history of introduction (i.e., the first variant was introduced first and so on).

## First Variant

Due to technical issues, the first variant is currently not available.

:::caution
The corresponding class (`JaMoPPJDTParser`) is still included in the artifacts. However, it only returns empty models.
:::

## EMF Proxy Objects

The second and third variant employ proxy objects and mechanisms built into EMF. Per default, EMF utilizes proxy objects to lazy load models persisted in different files and cross-referenced by other models.[^1] Nevertheless, the proxy mechanism is extensible. In general, a proxy object contains and is identified by a proxy URI. If then a reference with a set proxy object is accessed (i.e., the referenced element should be retrieved via a `get` method), EMF tries to resolve the proxy object by searching for the actual referenced element. If it is found, the actual element replaces the proxy object and is returned. Otherwise, the proxy object is returned.

## Second Variant

Although this variant is called *second variant*, it is based on and extends the reference resolution mechanism of the original JaMoPP.[^2]

:::info
When using the [`JaMoPPJDTSingleFileParser`](./parsing.md), the second variant is automatically active. It cannot be disabled.
:::

During parsing, the second variant creates a proxy object for every reference. The generated proxy URI has the format &lt;`Base URI`&gt;`/EMFTEXT_INTERNAL_URI_FRAGMENT_`&lt;`counter`&gt;`_`&lt;`identifier`&gt; where `Base URI` equals the URI of the model in which the proxy object is located, `counter` is the value of a proxy object counter incremented for every proxy object, and `identifier` is the identifier in the Java source code pointing to the actual Java element. In addition, the second variant stores the context of the proxy object independently from the models, including, for instance, the container of the proxy object or the reference for which the proxy object is set.

:::caution
If Java models with proxy objects are saved on disk, the proxy objects' context is not stored. As a result, if such models are loaded again in a new process, the context is not available, and the proxy objects can potentially be not resolved.
:::

Analogously to default EMF proxy objects, proxy objects created by the second variant are resolved when their corresponding reference is accessed. Then, the second variant walks up the model hierarchy, starting from the proxy object's containing element, to find the actual element. If the actual element resides in another Java file (i.e., in another model), and there is no model for the Java file, the second variant generates a logical URI for the model, which is tried to be mapped to a physical URI via the [`JavaClasspath`](./classpath.md). If this step succeeds, the extended JaMoPP [parses](./parsing.md) the additional Java file to search further in its model. By parsing the additional Java file, new proxy objects can be created within this paticular file.

## Eclipse JDT Bindings

Eclipse JDT Core can generate references between identifiers and their Java elements, too.[^3] In this case, the references are called *bindings*. They can represent a package, module, type, annotation, member value pair in an annotation, variable, or method and contain all information of the corresponding Java element. In addition, for missing elements, Eclipse JDT Core can partly recover bindings, which are then considered incomplete.

## Third Variant

At last, the third variant extends the second variant by a *binding-based resolution*. While it still creates a proxy object for every reference, the third variant utilizes the bindings generated by the Eclipse JDT Core to resolve proxy objects directly after parsing and before returning the models. Additionally, it can convert bindings to models if there is no model for the corresponding Java element. If there are proxy objects left after returning the models, the extended JaMoPP falls back to the second variant for resolution at a later point in time.

To enable or disable (and configure) the third variant, [parser options](./options.md) can be set.
